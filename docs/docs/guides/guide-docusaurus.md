# Guide Docusaurus — RestoForge

Petit guide de survie pour travailler proprement avec Docusaurus.
Ce fichier est à la racine du projet Docusaurus, **hors du dossier `docs/`**,
donc il n'apparaît pas sur le site publié.

## 1. Les commandes du quotidien

Toutes depuis `docs/` (la racine du projet Docusaurus, dans le monorepo) :

| Commande | Ce que ça fait |
|---|---|
| `npm start` | Serveur de dev sur http://localhost:3000, hot reload à chaque sauvegarde |
| `npm run build` | Build de production dans `build/` — **échoue si un lien est cassé** |
| `npm run serve` | Sert le contenu de `build/` pour tester le rendu final |
| `npm run clear` | Vide le cache `.docusaurus/` (à faire si le site a un comportement bizarre) |

Réflexe à prendre : **`npm run build` avant chaque commit**. Le serveur de dev
est tolérant, le build ne l'est pas (`onBrokenLinks: "throw"` dans notre
config). C'est lui qui dit la vérité.

## 2. Comment le site est organisé

```
docs/                             ← racine du projet Docusaurus (dans le monorepo)
├── docusaurus.config.ts          ← LA config : titre, navbar, footer, presets
├── sidebars.ts                   ← config de la sidebar (chez nous : autogénérée)
├── docs/                         ← ⚠️ le CONTENU du site (chaque .md = une page)
│   ├── intro.md
│   ├── adr/
│   │   ├── _category_.json      ← label + position du dossier dans la sidebar
│   │   ├── _template.md          ← préfixe « _ » : ignoré par Docusaurus
│   │   └── adr-001-monorepo.md
│   ├── architecture/             ← sections vides pour l'instant : elles
│   ├── guides/                      n'apparaissent dans la sidebar qu'à
│   └── modules/                     partir de leur première page
├── src/
│   ├── pages/index.tsx           ← la page d'accueil (React)
│   └── css/custom.css            ← surcharges CSS (couleurs, etc.)
├── static/                       ← fichiers servis tels quels (images, favicon)
├── build/                        ← sortie du build (gitignoré, ne jamais éditer)
└── .docusaurus/                  ← cache (gitignoré)
```

À retenir : **un fichier `.md` déposé dans `docs/` devient automatiquement une
page**, avec une URL calquée sur son chemin (`docs/adr/adr-001-monorepo.md` →
`/docs/adr/adr-001-monorepo`). Pas de déclaration à faire ailleurs.

Exception : **un fichier préfixé par `_` est ignoré** — ni page, ni entrée de
sidebar. C'est pour ça que notre modèle s'appelle `_template.md` : il reste
dans le dépôt comme modèle à dupliquer, mais ne pollue pas le site publié.
Attention en retour : on ne peut pas faire de lien Markdown vers un fichier
ignoré (le build échouerait) — on le mentionne en texte, entre backticks.

## 3. Anatomie d'une page

```markdown
---
sidebar_position: 1
---

# Titre de la page

Contenu en Markdown classique.
```

Le bloc entre `---` s'appelle le **front matter**. Les clés utiles :

- `sidebar_position: 2` — ordre dans la sidebar (sinon : ordre alphabétique
  des fichiers, c'est pour ça que nos ADR sont numérotés `adr-001`, `adr-002`…).
- `sidebar_label: "Nom court"` — libellé dans la sidebar si le titre est long.
- `slug: /mon-url` — pour forcer une URL différente du chemin du fichier.
- `draft: true` — la page est ignorée en build de production.

Le front matter est **optionnel** : une page sans front matter fonctionne très
bien (nos ADR n'en ont pas).

## 4. La sidebar : comment elle se construit

Chez nous, `sidebars.ts` contient une seule ligne utile :

```ts
docsSidebar: [{ type: "autogenerated", dirName: "." }],
```

Traduction : **la sidebar est le reflet du dossier `docs/`**. Un dossier =
une catégorie dépliable, un fichier = une entrée. Tu n'as jamais à éditer
`sidebars.ts` pour ajouter une page.

Pour contrôler une catégorie (un dossier), on pose un `_category_.json`
dedans :

```json
{
  "label": "ADR",
  "position": 2,
  "link": null
}
```

- `label` : le nom affiché dans la sidebar.
- `position` : l'ordre par rapport aux autres entrées du même niveau.
- `link: null` : la catégorie ne pointe vers aucune page (sinon Docusaurus
  peut générer un index automatique).

## 5. Liens et images, sans se planter

**Liens entre pages** : utilise des chemins **relatifs vers le fichier**,
avec l'extension :

```markdown
[le template](./adr/template.md)          ← ✅ vérifié au build, survit aux renommages
[le template](/docs/adr/template)         ← ⚠️ URL en dur, fragile
```

**Images** : dépose-les dans `static/img/` puis :

```markdown
![Schéma d'archi](/img/schema-archi.png)
```

Tout ce qui est dans `static/` est servi à la racine du site (`static/img/x.png`
→ `/img/x.png`).

Comme les liens cassés font échouer le build, tu ne peux pas en laisser
traîner — c'est une contrainte, mais c'est elle qui garde la doc saine.

## 6. Le piège n°1 : le Markdown est du MDX

Docusaurus compile les `.md` avec **MDX** (Markdown + JSX). 99 % du temps ça
ne change rien, mais certains caractères cassent le build :

| À éviter | Pourquoi | À la place |
|---|---|---|
| `<!-- commentaire -->` | commentaire HTML invalide en MDX | `{/* commentaire */}` |
| `<toto>` dans du texte | interprété comme une balise JSX | `` `<toto>` `` (backticks) |
| `{variable}` dans du texte | interprété comme une expression JS | `` `{variable}` `` |

Règle simple : **tout ce qui ressemble à du code va entre backticks**, et tu
n'auras jamais de problème.

## 7. Les admonitions (encadrés colorés)

Syntaxe spéciale Docusaurus, très pratique dans une doc :

```markdown
:::note
Une remarque neutre.
:::

:::tip
Un bon conseil.
:::

:::warning
Attention à ce point.
:::

:::danger
Ne fais surtout pas ça.
:::
```

## 8. `docusaurus.config.ts` : ce qu'il faut savoir

C'est le fichier central. Les zones qui te concernent :

- `title` / `tagline` — le nom du site (déjà réglés).
- `url` / `baseUrl` — à renseigner **au moment du déploiement** (l'URL
  publique). Tant qu'on ne déploie pas, on n'y touche pas.
- `presets` → `docs` — options du plugin docs ; c'est là qu'on a mis
  `blog: false` pour désactiver le blog.
- `themeConfig` → `navbar` / `footer` — les menus. C'est du JSON descriptif,
  pas du code : tu ajoutes une entrée en copiant une existante.
- `i18n` — on est en `fr`, ce qui traduit aussi l'interface Docusaurus
  (« Page suivante », etc.).

Après une modif de ce fichier, le serveur de dev redémarre tout seul, mais en
cas de doute : `npm run clear && npm start`.

## 9. Workflow type : ajouter un ADR

1. Duplique `docs/adr/_template.md` → `docs/adr/adr-004-mon-sujet.md`
   (sans l'underscore, pour que la nouvelle page soit publiée).
2. Remplis titre, statut, date, puis les trois sections
   (Contexte / Décision / Conséquences).
3. `npm start` pour vérifier le rendu — la page apparaît toute seule dans la
   sidebar, au bon endroit grâce à la numérotation.
4. `npm run build` pour valider (liens, MDX).
5. Commit. C'est tout : pas de config à toucher.

## 10. Ce qu'on ne fait PAS (pour rester clean)

- **Ne jamais éditer `build/` ni `.docusaurus/`** — régénérés à chaque build,
  et gitignorés.
- **Ne pas toucher au thème pour l'instant** (couleurs, logo) — prévu plus
  tard avec forge-ui.
- **Ne pas créer de page sans passer par `docs/`** — `src/pages/` sert aux
  pages spéciales (accueil), pas à la documentation.
- **Ne pas modifier un ADR accepté** — on écrit un nouvel ADR qui le remplace,
  et on passe l'ancien en statut « remplacé par ADR-XXX ».
